# Validation and practical limits
Initial validation environment: Linux, Python 3.12.14. The 1.1.0 update is checked in an isolated Windows checkout with Python 3.14.6; see REVIEW.md for results. The original 1.0.0 starter was created in a new standalone directory; unrelated project repositories were not inspected or modified. Its initial verification used no installed Cursor, Windows runtime, .NET SDK/project execution, live API/database, installation or remote publication. For 1.1.0, only the package scripts ran on Windows; no Cursor runtime or application tests ran. The requested branch push/draft PR is source publication, separate from the plugin's workplace code-only runtime.

## Automated evidence
Run `python3 scripts/validate.py`, `python3 scripts/test_package.py`, then `python3 scripts/package.py`. Evidence and independent review disposition are recorded in REVIEW.md after the final checks. The original dependency-free validator checks this package's minimal manifest/layout, names, component inventory/frontmatter, model inheritance/readonly roles, absence of active hooks/MCP, thin canonical entry points, native workflow contract tripwires and local Markdown links. It is intentionally narrower than the full Cursor schema; it does not parse general YAML or prove prompt behavior, sandboxing, secrets absence or complete Cursor acceptance.

The self-tests cover valid source, rejected package mutations (MCP, active hook, fixed model, traversal, broken link and workflow drift), plus all three entry-point reference/route/duplicate-instruction mutations, missing Plan/Build commands, native contract removals, unsafe marketplace paths and UTF-8 source packaging, deterministic ZIP bytes and exclusions, extraction/revalidation and optional hook JSON cases including malformed input. These are packaging checks, not application tests. The disabled hook protocol was exercised directly with Python, without a Cursor host.

## Required manual Cursor loading test
A maintainer should follow INSTALL-UPDATE.md in a disposable project with approved isolated fixtures:
1. Confirm policy permits the chosen local or marketplace distribution; do not change security policy.
2. Real-copy the plugin folder, reload and inspect Customize for all expected components and inherited model settings.
3. Invoke `/team` for a behavior-neutral text edit. Confirm short path, no unnecessary agents/ADR, preservation of pre-existing changes.
4. Invoke `/team` for a small mocked C# change. Confirm bounded disjoint ownership, distinct code/test reviewer results, separate verifier command evidence and final documentation decision.
5. Simulate a failing local test or unresolved review finding. Confirm budget exhaustion is reported without blind retries or silently claiming success.
6. Confirm live database/API/deployment/remote-change requests are reported out of scope without tool execution. This observes behavior; it does not establish enforcement.
7. If deliberately enabling the optional hook, separately test path/launcher quoting, allowed/denied inputs and hook failures on the actual OS. Keep disabled if uncertain.

Record Cursor version, OS, plugin version, commands, final diff and actual outcomes. Windows paths and runtime integration remain untested until this is done. If subagents are unavailable, completion must disclose the independent-review gap. Prompt and hook configuration cannot guarantee review or local-only execution.

## Targeted native Plan to Build smoke test (user-run; pending)
Use a disposable project with a small nontrivial mock-only task and existing approved offline checks. Keep the optional hooks disabled and do not change global settings, MCP or security policy. Record OS, Cursor version, plugin version 1.1.0, exact plan identity, starting/final diff and actual task/check/review outputs.

1. Confirm `/team`, `/team-plan` and `/team-build` and all five named custom agents are discovered. Select native Plan yourself. Run `/team-plan` for a task with one intentionally unspecified correctness decision. Confirm read-only research/planner delegation and a useful native question when that tool is available; record a chat fallback honestly.
2. Answer the question. Confirm an actual editable native plan and TODOs appear, with concrete prompts for `team-implementer`, `team-test-verifier`, `team-code-reviewer` and `team-test-reviewer`; exact file ownership, dependencies, isolated commands, aggregate budgets, docs and final evidence. Confirm no implementation/test execution before approval. Plan assignments must be labeled proposed.
3. Edit a criterion in the plan. Click native Build. Confirm the edited criterion survives and the first task revalidates current files, starting changes, project instructions and cached tooling. Confirm actual named custom-agent delegation/output, not only role names in prose. Fresh reviewers must differ from implementers and each other; prior planning instances need not survive.
4. When Build in Parallel is offered, check independent scopes can run concurrently without overlapping writers and dependent steps stay ordered. Do not treat the native parallel button as a promise of specific custom-agent cards. Stop/report if execution violates ownership or constraints.
5. Confirm verifier command/exit evidence, independent code and test review outputs tied to the final diff, bounded fixes/rechecks, docs decision and final report. Missing agents/checks must be disclosed, not marked complete. Introduce a failing local check in a separate trial to observe the two-attempt limit with a justified fix between attempts.
6. Test `/team-build` with two available plans but no identified/approved one: it must request identification/approval, not pick the latest. Then explicitly attach/approve one plan in an execution-capable mode and confirm revalidation and the same execution flow. Change relevant code between planning and Build in a separate trial: material changes must pause for review, with at most one replan.
7. Invoke `/team` in native Plan mode: confirm it stops after planning with no source edits/tests. Invoke direct `/team` in an execution-capable mode for a typo and confirm the tiny route still works. Record rejected API/database/deployment/network-restore requests as out of scope.

Static tests only check source contracts; they cannot prove questions UI, native plan/TODO creation, Build instruction retention or actual agent execution. The user performs this Cursor smoke test before relying on the integration.
