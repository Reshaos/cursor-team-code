# Canonical team workflow
This skill is the single source for `/team`, `/team-plan` and `/team-build`. Accept the plain-English request. Apply the code-only rule and selected project's applicable AGENTS.md, including nested instructions. Explain the goal and next action in plain language.

## Entry points and mode boundary
- `team`: direct end-to-end workflow below, sized proportionately. If invoked in native Plan mode or any read-only context, use the planning route and stop after planning; never override the mode's read-only boundary.
- `team-plan`: planning only. The user selects native Cursor Plan mode with the mode picker or Shift+Tab before invoking it. Commands and skills are prompts; they cannot programmatically switch modes. If not in native Plan mode, ask the user to select it before producing the native plan; do not silently implement or present ordinary chat text as a native plan.
- `team-build`: explicit fallback in an execution-capable mode. Require the user to identify/attach the approved plan by path, attachment or an unambiguous plan reference and confirm that version is approved. Never silently select the latest arbitrary plan. If absent, ambiguous or unapproved, request the missing identification/approval and pause dependent work. In Plan/read-only mode, inspect only and ask the user to select an execution-capable mode before execution.
- When this skill is invoked without an entry point, follow `team` while respecting the current mode.

## Planning route
Perform discovery and sizing below with read-only tools. For nontrivial tasks delegate read-only code research and planning to `team-planner`; give it the request, relevant paths, constraints and requested outputs. The coordinator synthesizes its findings and owns user questions. Use the native ask questions tool when available for missing decisions affecting correctness, scope or safety; otherwise ask concise chat questions. Do not invent tool names, force questions when nothing is missing, or promise a particular question/agent-card UI. Never delegate implementation, run state-changing checks or edit source during planning. Native plan creation/editing is the planning artifact exception, not permission to edit project files.

Create the actual native editable plan and native TODOs through the facilities available in the installed Cursor build. If unavailable, report that limitation, provide a clearly labeled draft, and stop; never claim the native plan was created. The plan must be self-contained for a future Build session. Include the following concrete, task-specific content rather than placeholders or just a reference to this skill:

1. **Identity and context:** descriptive plan title/reference, selected project, inspected baseline revision and starting diff, request, acceptance criteria, unresolved decisions, approved exclusions and documentation impact. Pending decisions block dependent Build steps.
2. **Execution contract:** copy the local code boundaries and aggregate budgets below into the plan, together with applicable project constraints. Carry them in the plan body so a new Build session does not depend on this skill remaining attached. Preserve starting user edits; do not reset, clean, stash or overwrite them.
3. **Agent task assignments and TODO graph:** assign stable task IDs, named roles, concrete delegation prompts, exact allowed files (including any proposed new files), required inputs/contracts, outputs, acceptance checks, dependencies and which tasks can run concurrently. Maximum three independent implementation scopes and one writer per file; sequence shared-file work. Label assignments as proposed, not actual spawned tasks. For the full route, include `team-implementer`, `team-test-verifier`, fresh `team-code-reviewer` and distinct fresh `team-test-reviewer`. Record the tiny route explicitly when justified; it uses coordinator implementation and self-review.
4. **Build instructions:** copy and specialize the entire execution procedure below (steps 4-8, review separation, fixes, docs and final checks), including exact approved local check commands, working directories and isolation basis. Expand the relevant-docs and finalchecks instructions into task-specific plan text: inspect checks for side effects, use cached tools only, preserve user edits, check the final diff/whitespace, maintain relevant feature maps/ADRs only when warranted, capture exits/results and skipped-check reasons, and invalidate affected evidence after later code edits. Do not rely on skill names alone for these steps. Do not merely say 'run /team-build' or expect a magic command callback. Make the first execution TODO revalidate the approved plan against current code, starting changes, AGENTS.md, ownership and available cached tooling; if the code/constraints changed, assess whether the plan still applies. Use at most one replan; material scope or acceptance changes require user review before dependent work. Explicitly require actual delegation to the named custom agents when available; new agent instances receive full prompts and constraints, not assumed memory from planning. If unavailable, disclose the sequential self-review fallback and independent-review gap.
5. **Evidence TODOs:** verification results tied to the final diff, separate reviewer outputs and disposition, bounded fix/recheck work, relevant documentation decision and final report. Every TODO specifies a completion condition; a proposed review assignment is not completed review evidence.

Stop after producing the plan for user review. Do not start execution until the user approves it through native Build or explicitly approves the identified plan for `/team-build`. Native Build follows the embedded instructions directly; it does not require a callback to a slash command or reuse the planning agent instances. Cursor's Build in Parallel controls native task execution when offered; retain ownership/dependency limits even there. UI and named-agent behavior require an installed-build smoke test.

## Execution admission and portable boundaries
For native Build and `team-build`, read the exact approved plan and perform its revalidation TODO before any edits. For direct `team`, discover and plan below. If identity, approval, isolation or file ownership is unclear, pause dependent work and report the smallest missing decision. Record actual spawned tasks separately from planned assignments; never mark TODOs complete based solely on a delegation proposal.

All work is local code only: no application APIs, real databases, Azure resources, service desks, deployment, remote mutations (including remote Git/PR creation), paid APIs, credential/security changes, dependency installation, downloads or network restores. Use existing cached tooling and approved isolated mocks/fixtures; inspect scripts and test setup before execution. A missing dependency or unproven isolation blocks that check. Pass these boundaries, applicable project instructions and the aggregate budgets to every worker and embed them in every native plan. Prompts do not enforce a sandbox.

## Execution procedure

1. **Discover** the selected project, applicable AGENTS.md, relevant feature map/ADRs and local command evidence. Inspect relevant files and existing changes. Ask only for missing requirements that affect correctness or safety. Never assume approval for live systems. Capture acceptance criteria and an in-memory work record: task, baseline revision plus starting diff, file ownership, approved checks, budgets and blockers.
2. **Size** the change. A tiny behavior-neutral correction in one file uses a short plan, one implementer (the coordinator), focused self-review and a proportionate approved local check. No agents, ADR or new test just to mirror wording. Any behavioral, multi-file or uncertain change uses the full route. If a tiny change expands, promote it.
3. **Plan** using the read-only team-planner for nontrivial direct work (or use the revalidated approved native plan). Define acceptance criteria, dependencies and each scope's exact allowed files, inputs, outputs, exclusions and check plan. Limit to three independent implementation scopes, with one writer per file. Delegate only genuinely independent scopes concurrently. Sequence shared-file work and contracts; do not parallelize overlapping writes. Existing user changes must be called out and preserved.
4. **Implement** using team-implementer per approved scope. Pass the same code-only limits to every worker. Do not delegate broad goals without file ownership. Stop workers on a discovered overlap or changed contract, then replan. Integrate locally and inspect the whole diff.
5. **Verify and review separately.** Use team-test-verifier to run only approved isolated local checks (it can write test outputs, unlike readonly reviewers). Then invoke a fresh team-code-reviewer and a distinct fresh team-test-reviewer, neither of which authored the implementation. Give both the request, acceptance criteria, exact final diff including relevant starting changes, and command evidence. Code review checks correctness/maintainability; test review checks coverage and isolation. Reviewers inspect code/evidence without edits or state-changing shell commands. If agents are unavailable, perform clearly labeled sequential self-review and state independent review was unavailable; never claim the full independent route passed.
6. **Fix with bounds.** At most two fix-and-recheck cycles for the task after the initial review. At most two executions of any failing check, with a specific intervening justified fix; no blind retry. Reviewers reassess relevant fixes against a fresh final diff. Maximum one replan; stop on repeated same finding, exceeded budget, unclear behavior, ownership conflict or forbidden dependency. Report remaining issue, evidence, options and the smallest missing decision. Do not lower acceptance criteria or silently waive a failed review.
7. **Relevant docs.** Apply relevant-docs. Maintain an existing feature map for changed behavior. Add/update an ADR only for a durable architecture decision; never create churn for trivial edits. Project instructions remain in the project and are never baked into this global plugin.
8. **Final checks.** Apply finalchecks after code and docs are final. Any later code change invalidates affected check/review evidence. Both reviewers inspect the final relevant diff after all fixes. Report outcome, changed files, acceptance criteria status, checks with exit/results, distinct review findings and disposition, docs changed or why unnecessary, limitations and unresolved blockers. Distinguish complete from partial/blocked; never say tested or independently reviewed without evidence.

Budget summary: three independent implementation scopes; one replan; two fix cycles; two attempts per failing check. The coordinator owns the aggregate budget across workers. Pause dependent work when a scope decision is required; continue only independent authorized work. Configuration cannot guarantee compliance or review.
